Inputs & outputs

INPUT — what the user must give

  • input.txt — scenario file on the cluster (e.g. /net/…/PLKRA-PROJECTS/…/input.txt)
  • .simg — application container on the same cluster partition
  • Execution profile — Slurm module / account / partition / memory / CPUs / time
  • (Optional) JIRA board, assignee, notes

OUTPUT — what they get back

  • Live Runtime Console — terminal view, polled every 3 s
  • Job record: owner, node, Slurm job id, exit code, timestamps
  • Stored log file — mirrored into the persistent runtime store
  • Generated artifacts — indexed & listed on the console page
  • (Optional) JIRA ticket with Gemma AI summary of the run
Why it matters: no SSH, no sourcing, no Slurm flags. The console runs the vendor script as the logged-in user, survives laptop disconnects (tmux), and tells you why a run failed — because the vendor script always exits 0, the console sniffs the log for failure markers too.

3

Inputs & outputs

INPUT — what the user must give

  • kpi.json — JSON batch list of INPUT_HDF / OUTPUT_HDF pairs
  • or single HDF pair: input.h5 + output.h5
  • ConfigInteractivePlots.xml + InputsInteractivePlot.json — when plots enabled
  • Output directory + Slurm resources (pre-filled presets)

OUTPUT — what they get back

  • CAN KPI: per-log HTML with tabs (overview · per-sensor · KPI scores) + index.html with accuracy & F1 across logs
  • UDP KPI: KPI HTML per sensor via ZMQ server + live Interactive Plot
  • Plots: CAN → raw signals & distribution · UDP → live connected box view
  • Runtime Console record: log, artifacts, exit code — reusable
Golden rule: CAN KPI → CAN Interactive Plot · UDP KPI → Interactive Plot — the UI only offers the matching pair. And if the same scenario was already run, the reuse check opens the stored console instead of re-running (fingerprint match).
