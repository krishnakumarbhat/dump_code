Context

Why this platform exists

Today, running a resimulation or a KPI job means SSH-ing to a cluster, sourcing a virtual environment, remembering Slurm flags, and babysitting a terminal. This console removes all of that.

🚫 Before

  • Manual SSH + sourcing environments
  • Remembering module load slurm, partitions, accounts
  • Re-running everything by hand every time
  • Outputs scattered in unknown folders

✅ After (this demo)

  • One web console: /html dashboard
  • Resim Run, KPI, Interactive Plot, Hyperlink, RAG chat
  • Slurm resources picked from profiles & presets
  • Everything recorded in SQLite — logs, artifacts, reuse

🧩 Pieces

  • main_html — the browser UI you see
  • hpcc_main.py broker — queues & supervises jobs (port 9100)
  • SIMG containers — can_kpi, udp_kpi, intplot, rag

Message: the console is the single door. KPI runs go to Slurm compute nodes, never to the login node.
Part 1 · Resim Run

What a Resim Run is

A resimulation ("resim") job takes a customer scenario (input.txt) and a container image (.simg), then replays the simulation on the cluster under Slurm — and the console shows the whole thing live.

Part 1 · Resim Run

Resim Run — end-to-end flow

1 · Open Runtime Map → "Resim Run"From the dashboard open Runtime Map; the Resim Run form is right on top. Click Detect to auto-fill cluster, project and partition from the paths.
2 · Fill paths & optionsPaste the input.txt and .simg paths (or use the Browse picker), pick an execution profile, optionally check "Create JIRA ticket".
3 · Submit“Run Resim” → the app validates same-partition paths, writes a unique job log, and launches an SSH background worker.
4 · SSH as youThe worker runs trig_helios.sh input.txt image.simg highPrio b02/b04 on your behalf (stored credentials via askpass), auto-answering “Y” prompts, with a 30-min safety timeout.
5 · Live consoleYou land on the Runtime Console page: the log tails every 3 seconds, and the owner can even send keystrokes (or Ctrl+C) into the running tmux-backed session.
6 · ResultStatus becomes COMPLETED (exit code + failure-marker sniffing, since the vendor script always exits 0). JIRA ticket auto-created if enabled.

Part 2 · KPI in brief

KPI in one minute

KPI = Key Performance Indicators: numbers that tell us whether the sensor data recorded by the simulation matches reality (reference). It compares an input HDF against an output HDF and produces an HTML report with scores.

input.h5→ KPI engine→ KPI report.html

Per sensor: Precision · Recall · F1 · Accuracy · Overall match %, plus scan counts and per-signal comparison.

Where do you run it?

Dashboard → KPI Analysis page. Pick the execution target, toggle the plots you want, fill paths, and press Queue through broker. The broker records the request in SQLite and spawns the container on Slurm.

How the KPI number is computed: detections from the input and output are matched scan-by-scan (exact 4-D alignment), then TP / FP / FN counts are turned into precision, recall, F1 and accuracy per scan, and finally averaged over all scans and all sensors.
Part 2 · KPI in brief

CAN KPI vs UDP KPI

CAN KPI

Controller Area Network data

  • Radar/sensor detection streams over CAN bus
  • Compares detection counts & signal values between input/output HDF
  • Output: tabbed HTML per log + index.html with per-sensor accuracy & F1 charts
  • Runs with CAN Interactive Plot (its own pipeline) — the generic Interactive Plot is not available for CAN
UDP KPI

UDP sensor streams

  • Sensor notifications delivered over UDP/ZMQ
  • KPI server exposes a ZMQ bridge; Interactive Plot subscribes and renders live
  • Output: KPI HTML per sensor, generated via the ZMQ server or JSON/HDF batch modes
  • Pairs with the generic Interactive Plot through the ZMQ bridge
CAN KPIUDP KPI
Data sourceCAN bus detection streamsUDP sensor notifications
Interactive plotCAN Interactive Plot (own pipeline, one broker request)Generic Interactive Plot over ZMQ bridge
OutputCAN KPI report + CAN Interactive PlotUDP KPI report + Interactive Plot

Part 3 · Interactive Plots

CAN Interactive Plot — raw data & distribution

Purpose: see the raw sensor data before trusting any KPI number. The CAN Interactive Plot renders every sensor's recorded signal over time so you can eyeball the distribution, the noise and the behavior.

What you can see

  • Raw signal traces per sensor (time series)
  • How values are distributed (histograms / spread)
  • Detection events and their timing
  • Input vs output overlay — spot drift instantly

How you debug with it

  • KPI low? → open the plot, check whether the signal exists at all
  • Empty / flat curves → sensor not parsed (see parse notices)
  • Offset curves → timing alignment issues between logs
  • Outliers → distribution view reveals them before they skew averages
Sequence for CAN: enable CAN KPI → enable CAN Interactive Plot → one broker request → CAN KPI report + CAN Interactive Plot are generated together in the same output directory.

Part 4 · Under the hood

How the KPI takes an average

1 · Align scansInput and output storage rows are aligned by scanindex — only common scans are compared (unmatched scans are counted and reported).
2 · Match detectionsEach scan's detection candidates are matched between input and output (4-D neighborhood hash match). Empty-vs-empty scans score 100%.
3 · Per-scan scoresTrue positives / false positives / false negatives → per scan: precision, recall, F1, accuracy, overall match %.
4 · Average itEach sensor's score array is averaged with nanmean → one number per sensor per metric.
5 · OverallThe sensor averages are averaged again → Overall Average Accuracy and Overall F1, shown on the index page and used for alerting (< 60% → JIRA ticket).
nanmean
per-sensor score arrays → one number per metric
mean
sensor averages → overall accuracy / F1
<60%
accuracy threshold → auto JIRA ticket

Part 5 · Reuse

Reuse — never trigger the same run twice

Before submitting, the KPI form asks the broker: “has this exact scenario already run?” The answer comes from a fingerprint of the request stored in SQLite.

1 · FingerprintSubmit → the app hashes tool + mode + all input/output paths + resources → request_fingerprint.
2 · Reuse-checkA dialog appears: “This scenario is already present — Owner, Status, Output, Stored log, Artifacts.”
3 · ChooseOK = generate again (deliberate rerun) · Cancel = open the stored runtime console instead — zero compute used.
4 · HistoryBoth paths create a history row; a reused job links back to the original runtime job (reused_from_runtime_job_id).
Why this matters: HDF pairs are huge and KPI runs cost Slurm hours. Colleagues on the same customer account immediately see that the result already exists — and just open the console. It also helps the team learn to run KPI by example: the history tab shows exactly what inputs previous runs used.

Preparation

Before you start — checklist

Environment

  • Console reachable: python hpcc_main.py then http://127.0.0.1:5001/html
  • Broker healthy: 127.0.0.1:9100 ping
  • Login as a demo user with cluster credentials stored (askpass needs them)
  • Slurm reachable from the UI (or local scheduler for fallback)

Demo data

  • One known-good input.txt + matching .simg on the cluster
  • One kpi.json with a small HDF pair (fast run)
  • One completed KPI job from earlier — so the reuse dialog shows instantly
  • One intentionally-broken artifact (optional) to show failure markers
Fallback plan: if Slurm is slow, show the reuse dialog on a completed job and the history tab first — both are instant and prove the platform without waiting for a queue.
Wrap-up

Recap — one line per thing

Resim Run

Submit input.txt + .simg from a form; the console SSH-runs the vendor script as you, under Slurm, with a live terminal and full history.

CAN KPI

Detection-match scores (precision / recall / F1 / accuracy) for CAN radar sensors, per log, plus an index across logs.

UDP KPI

Sensor KPI over a ZMQ bridge, feeding the live interactive plot; same averaging logic, different transport.

Interactive Plots

CAN: raw data & distribution for debugging. UDP: live connected box-view. Each pairs with its own KPI — never mixed.

Averages

Align scans → match detections → per-scan metrics → nanmean per sensor → overall average; <60% auto-opens a JIRA ticket.

Console & Reuse

Every run gets a live console and persistent record; identical scenarios are detected by fingerprint and reuse the stored result instead of re-running.
